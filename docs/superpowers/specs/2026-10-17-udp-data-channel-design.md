# UDP 数据通道：设计说明

日期：2026-10-17
状态：待评审
方案：A（TCP 控制 + 加密 UDP 数据），**不做自动回退**

## 一句话总结

控制连接仍然走 TLS over TCP —— 负责认证、心跳、会话管理、上报 UDP 端口；
**数据包改走 UDP**，用 AES-GCM 加密，密钥从已完成的 TLS 会话里导出。
目的：让交互流量（DNS、游戏、语音、网页请求）不再受 TCP 队头阻塞和重传退避的拖累。

## 为什么做：同一条线路上实测出来的

2026-10-17 20:52 晚高峰，同一台云服、同一时刻：

| 测试项 | 结果 |
|---|---|
| **UDP 小包（32B）** | **38/40 到达，平均 204ms**（177~241） |
| **UDP 大包（1400B）** | 31/50 到达，**丢 38%** |
| **UDP 大流量**（400×1400B） | 收回 350，**丢 12%** |
| **TCP 62233 握手** | 平均 **3129ms**，最差 7346ms |

**同一时刻，UDP 小包比 TCP 快 15 倍。** UDP 没有被封（95% 到达）。

但大包照样丢 38% —— 所以这个通道的价值在**交互流量**，不解决大文件下载。

## 方案结构

```
┌───────────── 控制通道（TCP + TLS 1.3 + mTLS）─────────────┐
│  HELLO / HELLO_ACK        会话建立、拿到 ack                 │
│  PING / PONG              心跳（面板上那个延迟）              │
│  TypeUDPPort(0x07)        客户端上报自己的 UDP 端口            │
│  断线检测、会话生命周期                                      │
└─────────────────────────────────────────────────────────────┘
┌───────────── 数据通道（UDP + AES-GCM）──────────────────────┐
│  TUN 收到 IP 包 → 加密 → UDP 发出        （不可靠，不重传）   │
│  UDP 收到 → 解密 → 写 TUN                                    │
└─────────────────────────────────────────────────────────────┘
```

**数据面故意不做可靠性。** 隧道传的是 IP 包，内层应用（TCP）本来就在重传和流控；
再叠一层可靠传输，就是"两层 TCP 各管各的重传" —— 那正是之前那个 13.6 秒延迟的来源。

## 与 OpenVPN 的对照

OpenVPN 的 UDP 模式结构与本方案几乎一致，只有一处关键差异：

| 维度 | OpenVPN | 本方案 |
|---|---|---|
| 控制通道载体 | **UDP + 自建可靠层（ACK + 重传）** | **TCP（内核负责可靠）** |
| 控制消息加密 | TLS 密文套在可靠层里 | TLS 直接在 TCP 上 |
| 数据通道 | UDP + 对称加密，**不可靠** | 同左 |
| 密钥来源 | TLS 会话里交换随机材料（key method 2） | **TLS 会话导出（RFC 5705）** |
| 防重放 | 序号 + 滑动窗口 | 同左 |
| 多客户端 | `P_DATA_V2` 的 24 位 peer-id | 按来源地址分派 |
| 抗 DoS | `--tls-auth` HMAC + SYN cookie | 见"可选增强" |
| NAT 保活 | `--ping` | 必须自己做 |

官方协议文档里这句是本方案的设计依据：

> the data channel is an unreliable channel while the control channel is a reliable channel

**为什么不学 OpenVPN 在 UDP 上自建可靠层**：那是为了"全 UDP"（连握手也不暴露 TCP
特征）。而实测这条线路上 **TCP 能连**（只是慢），所以直接用内核 TCP 做控制，**少写
几百行重传/ACK/窗口代码，也少一堆状态机 bug**。

## 详细设计

### 1. 密钥派生（已有，直接用）

两个方向各从 TLS 会话导出 32 字节：

```go
c2sKey, _ := tlsState.ExportKeyingMaterial(proto.UDPLabelC2S, nil, 32)
s2cKey, _ := tlsState.ExportKeyingMaterial(proto.UDPLabelS2C, nil, 32)
```

- 认证由 TLS 证书完成，**不自己写密钥交换**（那是安全关键代码）
- 两方向分开，避免同一密钥在两个方向复用 nonce 空间
- 实现位置：`server/udprelay.go:60-67`（已完成）

### 2. 会话绑定（防冒充）

服务端 `addSession(tlsState, ip, port)`：

- `ip` **只取 TCP 连接的真实远端**，不接受客户端声称 —— `udprelay.go:57-58` 已写清理由
- `port` 由控制通道的 `TypeUDPPort` 帧上报
- 按 `ip:port` 建索引，**不认识的来源直接丢**（否则谁发个包都能往隧道里灌数据）

### 3. 数据包格式（已有）

```
[8 字节序号（明文）][AES-GCM 密文 + 16 字节认证标签]
```

序号明文可见（同 WireGuard）—— 只泄露"这是第几个包"，换来接收端不必解密就能判重放。
AAD 里带方向字节，两个方向的密文不能互换使用。

### 4. 防重放（已有）

64 位滑动窗口（照 IPsec 做法）：窗口内乱序照收，重复包丢弃，窗口外的老包丢弃。

### 5. NAT 保活（**新增，硬要求**）

UDP 无连接，家宽 NAT 的空洞通常 30 秒~2 分钟就关。所以：

- 客户端**每 15 秒**发一个保活包（加密后的空负载即可）
- 服务端收到后回一个，**同时刷新 NAT 双向状态**
- 连续 **45 秒**收不到对端任何包 → 判定通道失效，记日志并提示"UDP 通道失联，请切回 TCP"

### 6. 会话生命周期

- 控制通道断开 → UDP 会话**随之移除**
- 客户端重新 HELLO（换 sid）→ 旧 UDP 会话**必须移除**，否则旧地址仍能注入数据
- 当前 `udprelay.go` **没有会话过期清理**，这是要补的

## 代价与风险（必须接受）

1. **大流量会变慢** —— 实测大包丢 38%。纯 UDP 模式下大文件下载会比现在差。
2. **UDP 被封就无法使用** —— 按要求**不做自动回退**，届时手动把连接码切回 `tcp`。
3. **NAT 保活是硬要求** —— 不做的话服务端的数据进不来。
4. **没有拥塞控制** —— 客户端以固定速率发；高丢包时可能加剧链路拥塞。
   缓解：按丢包统计降速（后续可选）。

## 可选增强（本期不做）

- **`--tls-auth` 式 HMAC 防火墙**：所有 UDP 包（含首个）加 HMAC，快速丢弃伪造包。
  当前 `Cipher.Open` 已能低成本丢重放（序号明文），但伪造包要走到解密才能证伪。
  公网被扫描风险高时再加。
- **key_id 轮换**：OpenVPN 用 3 位 key_id 支持无缝换密钥。本方案密钥绑定 TLS 会话，
  会话不换就不换。除非要长期运行且轮换密钥，否则不做。
